# Pairvu 完整产品升级方案（2026-10-10）

本方案依据用户提供的产品分析、仓库实现和生产审计。执行状态以 [生产核实与剩余任务](production-status-and-backlog-2026-10-10.md) 为准；研发调度以 [自动化协议](../../operations/README.md) 和机器任务清单为准。它是下一阶段方案，不表示下述功能已经上线，也不批准变更价格或生产发布。

## 1. 产品判断与报告校正

Pairvu 已跨过单图检测原型阶段，具有批量检测、自助订阅、内容入口和初步产品资产复用。下一阶段定位为：帮助商品团队依据 SKU 真实资料，对生成商品图作出可追溯的发布决定。最关键的缺口是可版本化的产品标准、可解释的证据、人工决策闭环和工作流接入。

| 报告观点 | 核实与处理 |
|---|---|
| M1 基本完成 | 生产有主流程验收记录，但标准加量包真实购买和当前付费客户验证尚未完成；不得把代码完成写成商业验证完成。 |
| 尚无 SKU Library | 需修正：已有 saved products、参考图版本与复用事件；升级应扩展现有实体，避免平行重建。 |
| 可立即推进发布门禁/API | 方向合理；先冻结证据及人工决定协议，再开放鉴权、幂等、额度和 webhook。 |
| SEO 流量、搜索量具体数值 | 来自用户报告，本轮未重跑 DataForSEO/广告或站点分析；作为待验证输入，不作为投资回报事实。 |
| 新定价与付费意愿 | $149–249 Studio、$299–999 API 等是实验假设，保留当前套餐，另行业务决策。 |
| 自动修复、多行业扩展 | 延后；先提高检测可信度、实际复用和人工审核效率。 |

生产审计还发现 Worker 缺少可核对的 Git SHA 标识。GitHub main 与本地基线一致并不能证明线上精确源码一致，因此第一项工程工作应补齐版本可追踪性。

## 2. 市场依据与战略选择

Photoroom 公布的保真评测涉及 850 个商品、3,400 张图片、10 位标注人员；其最佳模型 29% 和图层方式 38.2% 的通过结果来自特定虚拟试穿评测，不能泛化为所有商品图的行业错误率。[原始研究说明](https://www.photoroom.com/inside-photoroom/nobody-returns-a-photo)

Photoroom 已向企业提供可配置检查条件、通过/修复/人工复核流程的 Visual QA 能力。Pairvu 的差异化应集中在团队自己的 SKU 真值、区域证据、历史决定和轻量工作流，而非仅声称“能检查 AI 图片”。[Fidelity Raters API](https://www.photoroom.com/api/fidelity-raters-api)、[Visual Agents](https://www.photoroom.com/enterprise/visual-agents)

优先客户：电商内容代理商、商品摄影工作室、每月处理数百张以上素材的消费品团队。生成工具供应商作为 API 合作验证对象。先聚焦现有包装商品范围，不同时扩展服装、家具、视频和所有渠道合规。

价值主张：团队一次建立产品标准，多次检查，看到差异依据，留下人工决定，并把结果送回工作流。检测结论不是法定认证，也不自动代表所有平台可发布。

## 3. 目标产品与数据模型

| 模块 | 交付内容 | 验收边界 |
|---|---|---|
| SKU 产品标准 | 在现有 product 上增加品牌、名称、变体、容量、包装版本、关键/允许变化属性；多视角参考与生效版本 | 历史检查绑定不可变快照；更新参考不改写旧结论；workspace 所有权验证 |
| 参考匹配 | 候选视角与参考覆盖判断、可解释选择、手动纠正 | 无匹配/低可见性进 REVIEW；先 shadow 对比，不静默替换现有规则 |
| 区域证据 | 预期值、观测值、双方图片定位、可见性、严重程度、建议动作、置信信息 | 区域不可定位可明确为空；模型自报置信度不当作校准概率；不得生成不存在的文字证据 |
| 人工审核 | Approve/Reject、原因与备注、撤销后的新决定；误报/漏报/刻意变化/参考错误/证据不足分类 | 保留机器原判；追加审计事件；不能覆盖历史；权限和并发版本校验 |
| 发布工作台 | 按待审/阻断/已决定筛选；SKU 与批次视图；规则版本和最终决定导出 | 检测 verdict、人工 decision、发布 eligibility 三者独立；人工批准不消除高风险原始证据 |
| 自动化接口 | scoped API key、签名上传、异步批次、状态查询、结果 JSON、幂等请求、配额 | 接入现有额度账本，不绕过订阅；跨 workspace 请求拒绝；取消/重试不重复扣费 |
| Webhook | 事务 outbox、签名、事件版本、重试退避、失败队列、人工重放 | 至少一次交付，消费者按 eventId 去重；防 SSRF；禁止把完整图片或敏感资料放日志 |
| 质量与价值分析 | 按 SKU、生产工作流/来源模型、问题、人工修正统计 | 图片来源模型与检测模型分字段；未知来源标 unknown；低样本不做排名 |

优先沿用当前应用、Worker、D1、对象存储和队列。迁移采用增量字段/表及回填检查，不为本轮引入独立微服务。建议的概念实体包括 product_profile_versions、reference_views、analysis_evidence、review_decisions、policy_versions、api_keys、webhook_outbox；最终表名由专项架构契约确定。

所有分析固定 productVersion、referenceVersion、detectorVersion、policyVersion。图片和证据继续服从现有保留/删除策略；用户删除或到期后保留何种最小非图片审计元数据须明确告知并按现行约束执行。反馈不默认用于训练，不擅自延长客户图片保存时间。API key 仅存摘要、可撤销、最小 scope；上传地址限时且绑定 workspace/对象。功能开关默认关闭，先内部 fixture，再授权试点。

## 4. 分阶段交付（90 天假设节奏）

时间是资源和验证条件满足后的参考窗口，不是承诺。每一阶段以出口条件决定是否推进。

| 阶段 | 参考窗口 | 产出 | 出口条件 |
|---|---|---|---|
| U0 事实与控制基础 | 第 1–2 周 | 发布版本标识、独立验收系统、指标口径、基准样本协议 | 候选代码与验收绑定；发布来源可追踪；数据使用边界明确 |
| U1 SKU 真值与证据 | 第 2–4 周 | 产品版本、多视角、关键属性、结构化证据 | 旧数据兼容；隔离/历史快照测试；证据可被人工核对 |
| U2 人工决策闭环 | 第 4–6 周 | Review、理由、发布工作台、导出、审计 | 机器与人工判定分离；权限/并发/不可变历史通过；试点可完成完整工作流 |
| U3 可接入工作流 | 第 6–9 周 | API、幂等批次、额度复用、webhook、示例接入 | API 威胁与负向测试；重试/重复消费/配额正确；至少一个授权伙伴接通 |
| U4 质量与商业验证 | 第 9–12 周 | 持续评测、来源分析、试点价值报告 | 有真实重复使用与付费意愿证据，决定扩大、调整或停止 |

客户验证并行：先完成 15 次访谈和 5 个设计伙伴招募，争取累计 1,000 张获授权候选图。访谈、外发邀请、付款均需要真实负责人执行或单独授权；开发系统只准备材料，不能虚构完成。访谈重点是当前审核耗时、漏放代价、处理量、真实资料质量、最终决策人及接入方式。未获得试点不阻塞离线协议设计，但阻塞“已验证客户价值”的结论。

## 5. 评测与验收方案

建立 300–500 对授权样本作为开发评测集，至少 100 对独立留出样本作早期观察；按 SKU/包装版本分割，避免同商品近似图泄漏。两名标注员独立标注，分歧仲裁，记录可观测性、错误类型和严重程度。真实图、刻意改动、无错误对照、视角不匹配和不可见字段均应覆盖；合成 fixture 只验证工程行为，不能替代真实质量指标。

关键错误漏放率 = 含可观察关键错误却被自动允许的样本数 / 含可观察关键错误样本数。另报总体覆盖率、REVIEW 比例、人工批准比例、分品类结果和置信区间，不通过增加 REVIEW 掩盖性能不足。初期漏放 <2%、后续 <1% 是目标，不能由小样本直接宣称达到：独立样本零漏放时，单侧 95% 上界近似 3/n；100 个关键错误样本约 3%，300 个约 1%。总留出集 100 对并不等于 100 个关键错误样本。

工程验收分层：契约/schema 与 fixture；跨 workspace/权限负向；生命周期与历史快照；幂等/并发/重试；最小浏览器用户旅程；部署后的目标 smoke。每个单元只跑与差分相关的测试，认证、计费、迁移、API 提高强度。失败不得降格为“完成但待补测试”。

## 6. 指标、商业实验与停止条件

北极星：每周产生最终发布决定的唯一商品素材版本数，排除内部测试和重复重试。由真实人工决定或已配置规则决定标记来源，不能直接用 analysis completed 代替。

试点目标：5 个伙伴、3 个连续使用 4 周、2–3 个愿付每月 $199 以上；SKU 复用 >70%、审核时间下降 >50%、合格且匹配输入 REVIEW <20%。全部是待验证目标，需记录基线、分母、样本规模和客户同意。当前没有活跃付费 workspace 的审计结果不能被新预测覆盖。

单次成本计算包括模型、存储、队列、失败重试、人工支持及支付费用；先记录实际分布，再决定检查包/API 用量和定价。保留现行账单产品，禁止自动新增 Stripe 价格或真实交易。若伙伴无重复使用、误报造成更多工时、关键漏放无法下降，应缩小品类/错误范围并重新评估，而不是增加页面或套餐掩盖问题。

## 7. 暂缓范围与旧计划关系

暂缓自动修图、视频、全品类、正式认证承诺、完整 DAM、复杂企业协作/SSO、大规模新增薄 SEO 页。现有生产安全、删除、计费正确性和已有客户问题仍优先处理；内容补齐只做与试点需求直接相关的证据案例。

本方案的 U0–U4 是升级阶段，不改写既有 M0/M1/M2 历史验收。原 R01–R15 审计剩余事项继续保留：R01 发布来源对应 UPG-01；支付和加量包验收保留人工门槛；现有 SEO/运营待办排在核心闭环之后，除非影响线上正确性。任务完成以证据而非旧路线图勾选为准。

## 8. 自动化执行与发布边界

总控维护唯一任务和候选版本；开发按契约提交本地代码；独立验收只审核固定提交，失败返同一开发任务。首个 AUTO-01 用于验证这套机制。活跃会话用 wait_threads 持续回收，派单后不结束等待；每小时 heartbeat 只作中断恢复并处理一个最小单元；本地机器、Codex 应用和项目须可用。[Codex Scheduled tasks](https://developers.openai.com/codex/automations/)

当前授权自动研发、离线验证和本地提交；运行时代码到 RELEASE_READY 停止，生产发布须另有明确授权，并完整执行仓库 AGENTS.md 的提交、推送、远端确认、迁移、部署及 smoke 顺序。审核 PASS、GitHub 合并与生产验收是不同事实。
