# JRN-03 local write isolation and eligibility acceptance

JRN-03 is a replayable **local-only synthetic** journey. The harness runs every app D1 migration in a fresh Miniflare/workerd D1, puts six synthetic PNG assets in a fresh local R2 bucket, signs in two `example.test` identities through actual Better Auth magic-link issuance and verification, and checks that their Free accounts have distinct workspaces. Mail is captured in memory. Any other `fetch` is rejected, and Miniflare outbound service returns 403. No `.env`, `.dev.vars`, production binding, Stripe input, external email, model call, payment, or customer asset is used.

Run from the repository root with a minimal child environment:

```sh
env -i PATH="$PATH" HOME="$HOME" TMPDIR="$TMPDIR" LANG="${LANG:-C.UTF-8}" pnpm exec tsx scripts/jrn03-journey.ts /private/tmp/pairvu-jrn03-dev-report.json
```

The report records its unique run ID, temporary storage location, A/B workspace IDs, synthetic asset/product/batch/analysis IDs, individual check results, and an `uiPage` path. It deliberately contains no cookies or magic links. The final development run is retained as [final-report.json](../../fixtures/journey-write-eligibility/final-report.json). The browser component check used a preceding passing run retained as [dev-report.json](../../fixtures/journey-write-eligibility/dev-report.json) and [ui-page.json](../../fixtures/journey-write-eligibility/ui-page.json). Each run allocates fresh temporary D1/R2 storage and disposes the worker on exit. The generated storage is retained under the named temporary directory for inspection until the system removes temporary files. The script makes no persistent production changes.

For the component check, use `node scripts/jrn03-ui.mjs /private/tmp/pairvu-jrn03-dev-report.json`, open its printed loopback URL in a browser, and inspect the actual `ReleaseWorkbenchClient` component. The server replays the saved local authenticated route response through an in-memory fixture transport. It does not authenticate a browser session or represent production browser E2E. The development browser observation is recorded in [ui-check.json](../../fixtures/journey-write-eligibility/ui-check.json).

The local route/D1 matrix covers actual product create, profile PUT, lifecycle PATCH, and reference POST with both owners; valid cross-account existing target writes in both directions; foreign reference IDs with valid bodies and forged owner fields; actual review POST approve/reject/revoke against completed analyses; replay and stale revision; actual batch PATCH cancel/retry against queued and failed items; queue counts and D1 snapshots around denials; and actual release GET before/after review. A has a frozen versioned product and batch/analysis source, six complete synthetic match observations persisted through the real risk policy and `persistCompletedAnalysis`, readable local R2 images, and a real review POST. The same release row moves `needs_review` → `eligible` with `complete_source_approved`, then `needs_review` on revoke and `eligible` on reapproval. Current SKU editing leaves its frozen source unchanged. B cannot see A's eligible row, and forged filters are rejected. The supported `state=decided` filter returns the eligible A row; the API does not define an `eligibility=eligible` filter.

Four isolated copy analyses prove that approval does not bypass missing observations, unavailable image, a high-risk difference, or changed machine source. The negative injections are at the **local D1 fixture layer**, after each copy receives an actual review POST. They never modify the positive A analysis. Model-call metadata rows and visual observations are explicitly synthetic provenance needed to exercise the release policy; no model was run. Thus `syntheticMachineEvidence=true`, `qualityEvidence=false`, and `modelCallsExecuted=0` in the report. `productionWriteIsolationCovered=false` and `productionEligibleCovered=false` remain until a separately authorized production acceptance supplies real evidence.

The development run passed 17 route/storage cases and the separate component check. Earlier development failures were harness mistakes, not product findings: full-database digest included Better Auth session activity; `NextRequest` rewrote loopback host to `localhost` for the review origin guard; the initial batch fixture lacked the batch-item analysis association; and two assertions used unsupported release response fields/statuses. The final harness checks the scoped mutation tables, uses matching loopback origin, binds the item, and checks the published release schema. Fixed-candidate independent acceptance remains required before closing JRN-03. No production release is authorized by this document.
